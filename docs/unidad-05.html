Unidad 05 · Apunte de lectura

Desarrollo de una DApp

Ana y Bruno van a usar el contador desde una página web. La aplicación conecta interfaz, proveedor, cuenta y contrato. Su tarea es mostrar qué se consultó, qué se autorizó y qué resultado obtuvo cada operación.

1. Del contador desplegado a una aplicación

En la unidad 04 creamos una instancia del contador y comprobamos su red, dirección, código y valor. Ahora Bruno quiere incrementar desde un botón y Ana quiere reiniciar desde una página. La interfaz facilita esas acciones, pero la regla de autorización continúa en el contrato.

Si la página oculta el botón de reinicio a Bruno, mejora la experiencia. No alcanza para proteger el estado. Bruno podría intentar la llamada por otra herramienta. El contrato debe seguir rechazándola por msg.sender, como se explicó en la unidad 03.

DApp significa decentralized application, o aplicación descentralizada. En nuestro ejemplo, una interfaz web utiliza un smart contract para guardar un estado y aplicar reglas que la red ejecuta. La página y los servicios de acceso también forman parte del sistema.

Usar un contrato no convierte automáticamente cada componente en descentralizado. El servidor que entrega la página y el proveedor RPC tienen sus propias condiciones de disponibilidad. El nodo local permite estudiar la integración. Una aplicación pública necesitaría decidir red, acceso, almacenamiento y operación del servicio.

2. Interfaz, proveedor, firmante y contrato

Componentes del contador conectado
ComponenteResponsabilidad
Interfaz, o UIMuestra valor, cuenta, red, acciones y estado de la operación. UI significa user interface.
Proveedor, o providerComunica con el nodo para consultar la red, código, estado y recibos.
Firmante, o signerUtiliza una cuenta para autorizar y enviar una operación.
WalletGestiona el acceso a cuentas y la autorización según su modelo de custodia.
ContratoEjecuta incrementar o reiniciar y comprueba las reglas.
Nodo y EVMProcesan llamadas y transacciones y ofrecen el estado de la red.

La ABI permite a ethers preparar los bytes de una llamada e interpretar su respuesta. La dirección selecciona la instancia y la red determina en qué estado se busca. Ninguna de esas tres piezas concede el permiso de propietario.

La interfaz del curso permite Conectar cuenta local. Usa JsonRpcProvider con el nodo en 8545 y obtiene un signer de una cuenta de desarrollo gestionada por ese nodo. Por eso no aparece una ventana de MetaMask para cada operación. El nodo local autoriza las cuentas de prueba.

El botón Conectar wallet usa BrowserProvider sobre window.ethereum, la conexión que puede ofrecer una wallet instalada en el navegador. Solicita acceso a las cuentas y utiliza la cuenta autorizada por la wallet. Allí una escritura puede requerir confirmación de la persona.

La práctica obligatoria funciona con cuentas locales sin instalar una wallet externa. Ese acceso a cuentas de desarrollo no es un modelo para exponer un RPC con cuentas desbloqueadas en una aplicación pública.

3. Conectar con la instancia correcta

La interfaz carga despliegue.json desde su servidor local. El archivo fue generado en la unidad 04. Contiene chainId, contador, contadorTransactionHash y la ABI completa. No se inventa una dirección ni se usa la dirección de Ana como dirección del contrato.

Antes de habilitar botones hay que comprobar que el archivo y el proveedor corresponden a la red local 31337 y que la dirección tiene código. La comprobación de creación de la unidad 04 ayuda a reconocer la instancia. Si se reinicia el nodo, se redespliega, se actualiza el registro y se recarga la página.

Este ejemplo completo se ejecuta con npm run consultar desde laboratorio. Usa el mismo registro de la interfaz y un proveedor, sin obtener un firmante:

import {readFile} from 'node:fs/promises'
import {Contract} from 'ethers'
import {local} from './comun.mjs'

let provider
try {
  provider = await local()
  const config = JSON.parse(await readFile(new URL('../ui/despliegue.json', import.meta.url), 'utf8'))
  if (String(config.chainId) !== String((await provider.getNetwork()).chainId)) {
    throw Error('El registro corresponde a otra red. Volvé a desplegar.')
  }
  const codigo = await provider.getCode(config.contador)
  if (codigo === '0x') throw Error('La dirección no contiene código. Volvé a desplegar después del reinicio.')
  const contador = new Contract(config.contador, config.abi, provider)
  console.log('Red:', config.chainId)
  console.log('Contador:', config.contador)
  console.log('Propietario:', await contador.propietario())
  console.log('Valor:', (await contador.valor()).toString())
} catch (error) {
  console.error('Consulta no completada:', error.shortMessage || error.message)
  process.exitCode = 1
} finally {
  provider?.destroy()
}

new Contract construye un objeto JavaScript que conoce la dirección, la ABI y el medio de acceso. No crea un contrato en la red. await contador.valor() realiza una consulta al contrato que ya existe.

import {BrowserProvider, Contract} from '/vendor/ethers.js';

export async function conectarWallet(config) {
  if (!window.ethereum) throw new Error('No hay wallet disponible.');
  const provider = new BrowserProvider(window.ethereum);
  try {
    await provider.send('eth_requestAccounts', []);
    const red = await provider.getNetwork();
    if (red.chainId !== 31337n || BigInt(config.chainId) !== red.chainId) {
      throw new Error('Seleccioná la red local 31337.');
    }
    if (await provider.getCode(config.contador) === '0x') {
      throw new Error('No existe el contrato. Volvé a desplegar.');
    }
    const signer = await provider.getSigner();
    const contrato = new Contract(config.contador, config.abi, signer);
    return {provider, contrato, cuenta: await signer.getAddress()};
  } catch (error) {
    provider.destroy();
    throw error;
  }
}

El ejemplo se usa como módulo servido por la interfaz, con el registro cargado como argumento config. eth_requestAccounts solicita permiso para acceder a las cuentas. No revela la clave privada ni equivale a firmar una transacción. La comprobación de red evita operar por error en otra configuración.

Ana es propietaria porque creó la instancia. Bruno puede incrementar, pero no reiniciar. La interfaz debe mostrar la cuenta seleccionada y la dirección del contrato para que la persona pueda reconocer qué operación solicita.

En el modo local, el selector A/B se aplica al volver a conectar. En el modo wallet, opera la cuenta autorizada por la wallet, no la letra del selector local. Cambiar la cuenta de la wallet requiere invalidar la conexión anterior y volver a comprobar el contexto.

4. Consultar y mostrar el estado

const lectura = new Contract(config.contador, config.abi, provider);
const valor = await lectura.valor();
document.getElementById('valor').textContent = valor.toString();

Este fragmento presupone un registro config y un proveedor provider ya comprobados. Consulta valor() y muestra el resultado. Una consulta externa de este tipo utiliza eth_call, que simula la ejecución en el estado consultado sin registrar una transacción nueva.

Actualizar la página o pulsar Actualizar no cuenta como un incremento. Tampoco requiere una firma nueva ni una comisión de transacción para quien consulta. Si una lectura se ejecuta dentro de otra transacción, sí forma parte del trabajo de esa transacción.

ethers devuelve enteros de Solidity como bigint, un tipo de JavaScript para enteros grandes. El valor 2n representa el entero dos. El sufijo n indica bigint en el código, no forma parte del texto que verá la persona.

const valor = 9007199254740993n;
console.log(valor.toString()); // "9007199254740993"

El tipo Number no representa exactamente todos los enteros de ese tamaño. Para mostrar un entero se usa toString() sin convertirlo primero a Number. También hay que convertir explícitamente los bigint antes de guardarlos como campos de un JSON.

Si Bruno incrementa desde otra página, la pantalla de Ana no se actualiza por haber leído antes. Debe consultar de nuevo o utilizar un mecanismo de actualización. En la interfaz del curso se vuelve a leer después de una escritura exitosa y cuando se pulsa Actualizar.

El evento ValorCambiado permite estudiar quién hizo una operación, pero una notificación no sustituye por sí sola la lectura del valor actual. Las reglas y el estado siguen viviendo en el contrato.

5. Solicitar, enviar y comprobar una escritura

Bruno pulsa Incrementar con el contador en 2. La interfaz solicita la operación al signer. Si se autoriza y se envía, ethers devuelve una transacción con un hash. Todavía hay que esperar su inclusión y comprobar el recibo.

El receipt, o recibo, informa el resultado de ejecución de la transacción incluida. En este ejemplo, status === 1 permite informar que la ejecución fue exitosa y después consultar el valor 3. status === 0 corresponde a una ejecución revertida. Esa comprobación no equivale por sí sola a la finalidad de una red pública.

export async function enviarYConfirmar(operacion, estado) {
  estado('Esperando firma y envío…');
  const tx = await operacion();
  estado(`Pendiente de confirmación: ${tx.hash}`);
  const recibo = await tx.wait();
  if (!recibo || recibo.status !== 1) {
    throw new Error('La transacción no se confirmó correctamente.');
  }
  estado(`Confirmada: ${recibo.hash}`);
  return recibo;
}

operacion es una función que devuelve una promesa de transacción, por ejemplo () => contrato.incrementar(). estado es una función que muestra un mensaje. await suspende este recorrido hasta recibir cada resultado, sin bloquear todo el navegador.

tx.wait() espera el recibo. ethers puede lanzar un error si la ejecución revierte. La comprobación explícita también rechaza un recibo inexistente o con status distinto de 1. La función devuelve el recibo exitoso y deja que su llamador gestione los errores.

async function incrementarDesdeBoton(contrato, estado, boton, mostrarValor) {
  boton.disabled = true;
  try {
    const recibo = await enviarYConfirmar(() => contrato.incrementar(), estado);
    const valor = await contrato.valor();
    mostrarValor(valor.toString());
    return recibo;
  } catch (error) {
    estado(error.shortMessage || error.message);
    throw error;
  } finally {
    boton.disabled = false;
  }
}

Este ejemplo presupone un contrato y contexto de conexión válidos. Deshabilita el botón mientras se realiza la operación y lo restablece al terminar. El evento del botón debe manejar el error propagado para que no quede una promesa rechazada sin tratar.

En la aplicación completa también se comprueba que la cuenta o la red no hayan cambiado mientras se esperaba. Restablecer un botón a ciegas después de perder la conexión podría permitir una nueva operación con un contexto inválido.

6. Permisos, errores y cambios de contexto

Qué puede ocurrir con una operación
SituaciónQué evidencia hayQué debe comunicar la interfaz
Firma canceladaNo se obtuvo una transacción enviada.La persona no autorizó el envío.
Rechazo al estimar gasPuede no existir hash ni recibo.La llamada se rechazó antes del envío.
Transacción pendienteExiste hash, todavía no hay recibo comprobado.Está enviada y pendiente.
Reversión incluidaExiste recibo fallido o error de wait.La ejecución falló y sus cambios no se conservaron.
Nodo apagadoFalla la comunicación RPC.No se pudo consultar o completar la comprobación.
Red equivocadaEl chainId no coincide con el requerido.Corregir la conexión antes de operar.

Un fallo al consultar después del envío deja incertidumbre sobre la inclusión. No demuestra que la transacción nunca se ejecutó. Antes de repetirla hay que comprobar el hash en la red correspondiente.

Con el contador en 2, Bruno firma correctamente un reinicio. El contrato compara msg.sender con propietario y rechaza la llamada. El valor queda en 2. Si se detecta durante la estimación, la interfaz puede recibir un error antes de obtener un hash.

Ana sí puede reiniciar. La aplicación espera el recibo exitoso y consulta cero. El mismo código de gestión de espera sirve para ambas acciones. Lo que cambia es la regla que aplica cada función del contrato.

window.ethereum?.on?.('accountsChanged', () => {
  invalidarConexion();
  mostrarEstado('Cambió la cuenta. Reconectá la wallet.');
});
window.ethereum?.on?.('chainChanged', () => {
  invalidarConexion();
  mostrarEstado('Cambió la red. Reconectá la wallet.');
});

Este fragmento presupone funciones de la aplicación que limpian la instancia conectada, deshabilitan las operaciones y muestran mensajes. Los eventos avisan que las cuentas accesibles o la red cambiaron. Al reconectar se comprueba otra vez red, dirección, código y cuenta.

Una operación pendiente puede terminar después del cambio. Su resultado pertenece al contexto original. La interfaz del curso descarta resultados tardíos de conexiones anteriores y pide reconectar, en lugar de aplicarlos a la nueva cuenta.

Mientras se espera una escritura se deshabilitan acciones que podrían enviar otra solicitud con el mismo contexto. El botón vuelve a habilitarse cuando el recorrido termina y la conexión sigue siendo válida. Si el nodo dejó de estar accesible, se limpia la conexión y se informa el problema.

La UI debe diferenciar una escritura confirmada de una actualización visual fallida. Si el recibo ya indicó éxito pero la consulta posterior falla, el cambio puede haberse aplicado. Hay que reconectar y consultar antes de reenviar.

7. Usar el contador desde la página local

Partí del Contador completado y de una instancia verificada en la unidad 04. Desde laboratorio, una terminal mantiene el nodo y la otra inicia el despliegue y el servidor de la página:

# Terminal 1, mantener abierta
npm run nodo

# Terminal 2
npm run desplegar
npm run verificar:deployment
npm run interfaz

La segunda terminal informa http://127.0.0.1:4173 y queda ocupada por el servidor. Abrí esa URL en el navegador. El servidor entrega HTML, JavaScript, ethers y el registro de la instancia. El nodo en 8545 es otro proceso.

  1. Seleccioná A · propietaria del despliegue y pulsá Conectar cuenta local. Revisá red, contrato, cuenta y valor inicial 0.
  2. Seleccioná B · participante. La interfaz pide reconectar. Volvé a pulsar Conectar cuenta local.
  3. Incrementá dos veces, esperando cada resultado. Verificá 1 y luego 2.
  4. Con B, intentá reiniciar. Debe aparecer el rechazo y conservarse el valor 2.
  5. Seleccioná A, reconectá y reiniciá. Después del recibo exitoso debe leerse 0.
  6. Recargá la página y conectá otra vez. Mientras el nodo conserve esa sesión, se consulta el estado que quedó.

Para observar un período pendiente más largo se puede utilizar la simulación anterior. El nodo de desarrollo suele incluir operaciones rápidamente, por lo que algunos mensajes reales pueden durar poco en pantalla.

En el contador, el permiso de reiniciar tiene una condición simple. En la compra condicionada que motivó la unidad 02, la interfaz también debe identificar cuenta, instancia y estado antes de solicitar una acción. La confirmación del envío no sustituye la comprobación de la condición del contrato.

El mismo recorrido puede extenderse al caso de certificados: una interfaz consulta vigencia y una cuenta autorizada solicita emisión o revocación. Cambian el programa y sus estados, pero se conservan la identificación por red y dirección, la ABI, la espera del recibo y la consulta posterior.

8. Qué prueban los tests y qué se revisa en el navegador

La plantilla que se completa es laboratorio/ui/cliente.js. El contrato de la función es informar solicitud, pendiente y confirmada en ese orden, devolver el recibo exitoso y propagar errores. Los casos automáticos utilizan respuestas controladas para observar el comportamiento.

npm test -- Interfaz

Los tests comprueban que no se anuncie éxito mientras la promesa del recibo sigue pendiente. También comprueban el recibo devuelto, status fallido, recibo inexistente, rechazo de firma y error durante la espera. Los detalles aparecen en la terminal.

Los tests anteriores prueban la función con transacciones simuladas. No abren MetaMask ni verifican visualmente la página, la cuenta activa, el endpoint, la carga del JSON o cada botón. Para demostrar la integración hay que recorrer la interfaz contra el nodo y el contrato.

La revisión docente compara la matriz de casos, las evidencias y la explicación. Las pruebas de Contador y de Deployment cubren partes complementarias. Un estado verde de GitHub tampoco significa que estén resueltos todos los TODO: el workflow general ejecuta solo los casos indicados en su archivo.

  provider?.destroy()

new Contract construye un objeto JavaScript que conoce la dirección, la ABI y el medio de acceso. No crea un contrato en la red. await contador.valor() realiza una consulta al contrato que ya existe.

Unidad 05 · 3. Conectar con la instancia correcta

Conexión con una wallet en el navegador

import {BrowserProvider, Contract} from '/vendor/ethers.js';

export async function conectarWallet(config) {
  if (!window.ethereum) throw new Error('No hay wallet disponible.');
  const provider = new BrowserProvider(window.ethereum);
  try {
    await provider.send('eth_requestAccounts', []);
    const red = await provider.getNetwork();
    if (red.chainId !== 31337n || BigInt(config.chainId) !== red.chainId) {
      throw new Error('Seleccioná la red local 31337.');
    }
    if (await provider.getCode(config.contador) === '0x') {
      throw new Error('No existe el contrato. Volvé a desplegar.');
    }
    const signer = await provider.getSigner();
    const contrato = new Contract(config.contador, config.abi, signer);
    return {provider, contrato, cuenta: await signer.getAddress()};
  } catch (error) {
    provider.destroy();
    throw error;
  }
}

El ejemplo se usa como módulo servido por la interfaz, con el registro cargado como argumento config. eth_requestAccounts solicita permiso para acceder a las cuentas. No revela la clave privada ni equivale a firmar una transacción. La comprobación de red evita operar por error en otra configuración.

Unidad 05 · 4. Consultar y mostrar el estado

Qué es bigint y por qué usamos toString

ethers devuelve enteros de Solidity como bigint, un tipo de JavaScript para enteros grandes. El valor 2n representa el entero dos. El sufijo n indica bigint en el código, no forma parte del texto que verá la persona.

const valor = 9007199254740993n;
console.log(valor.toString()); // "9007199254740993"

El tipo Number no representa exactamente todos los enteros de ese tamaño. Para mostrar un entero se usa toString() sin convertirlo primero a Number. También hay que convertir explícitamente los bigint antes de guardarlos como campos de un JSON.

Unidad 05 · 5. Solicitar, enviar y comprobar una escritura

El hash no es un mensaje de éxito

Bruno pulsa Incrementar con el contador en 2. La interfaz solicita la operación al signer. Si se autoriza y se envía, ethers devuelve una transacción con un hash. Todavía hay que esperar su inclusión y comprobar el recibo.

El receipt, o recibo, informa el resultado de ejecución de la transacción incluida. En este ejemplo, status === 1 permite informar que la ejecución fue exitosa y después consultar el valor 3. status === 0 corresponde a una ejecución revertida. Esa comprobación no equivale por sí sola a la finalidad de una red pública.

Unidad 05 · 5. Solicitar, enviar y comprobar una escritura

Una función que conserva el orden

export async function enviarYConfirmar(operacion, estado) {
  estado('Esperando firma y envío…');
  const tx = await operacion();
  estado(`Pendiente de confirmación: ${tx.hash}`);
  const recibo = await tx.wait();
  if (!recibo || recibo.status !== 1) {
    throw new Error('La transacción no se confirmó correctamente.');
  }
  estado(`Confirmada: ${recibo.hash}`);
  return recibo;
}

operacion es una función que devuelve una promesa de transacción, por ejemplo () => contrato.incrementar(). estado es una función que muestra un mensaje. await suspende este recorrido hasta recibir cada resultado, sin bloquear todo el navegador.

tx.wait() espera el recibo. ethers puede lanzar un error si la ejecución revierte. La comprobación explícita también rechaza un recibo inexistente o con status distinto de 1. La función devuelve el recibo exitoso y deja que su llamador gestione los errores.

Unidad 05 · 5. Solicitar, enviar y comprobar una escritura

Usar el recibo y consultar después

async function incrementarDesdeBoton(contrato, estado, boton, mostrarValor) {
  boton.disabled = true;
  try {
    const recibo = await enviarYConfirmar(() => contrato.incrementar(), estado);
    const valor = await contrato.valor();
    mostrarValor(valor.toString());
    return recibo;
  } catch (error) {
    estado(error.shortMessage || error.message);
    throw error;
  } finally {
    boton.disabled = false;
  }
}

Este ejemplo presupone un contrato y contexto de conexión válidos. Deshabilita el botón mientras se realiza la operación y lo restablece al terminar. El evento del botón debe manejar el error propagado para que no quede una promesa rechazada sin tratar.

En la aplicación completa también se comprueba que la cuenta o la red no hayan cambiado mientras se esperaba. Restablecer un botón a ciegas después de perder la conexión podría permitir una nueva operación con un contexto inválido.

Unidad 05 · 6. Permisos, errores y cambios de contexto

Bloquear duplicados y recuperarse

Mientras se espera una escritura se deshabilitan acciones que podrían enviar otra solicitud con el mismo contexto. El botón vuelve a habilitarse cuando el recorrido termina y la conexión sigue siendo válida. Si el nodo dejó de estar accesible, se limpia la conexión y se informa el problema.

La UI debe diferenciar una escritura confirmada de una actualización visual fallida. Si el recibo ya indicó éxito pero la consulta posterior falla, el cambio puede haberse aplicado. Hay que reconectar y consultar antes de reenviar.

Unidad 05 · 9. Práctica guiada y decisiones de arquitectura

Qué datos pertenecen a cada componente

El contrato guarda valor y propietario. El registro de deployment guarda dirección, red y ABI. La UI puede guardar preferencias, como el tema visual, fuera de la cadena. La clave privada pertenece al medio de autorización, no al HTML ni al JSON de configuración.

Guardar un dato fuera de la cadena puede simplificar el sistema, pero introduce decisiones sobre integridad y disponibilidad. Ese diseño debe explicar quién administra cada parte y cómo se comprueba la coherencia.
